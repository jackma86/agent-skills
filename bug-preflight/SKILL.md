# Bug 修复前评审

先读取目标项目的规则、相关需求和已有缺陷记录，再依次执行以下步骤。

1. **分析 Bug。** 明确触发条件、预期与实际结果、影响范围。追踪相关入口和调用路径，结合代码、日志或测量定位原因，注明哪些判断仍需验证。
2. **实测 Bug 场景。** 在修改产品代码前运行最小相关场景，优先复用已有测试入口和隔离数据。记录版本、环境、数据前提、操作和结果。性能问题记录可比较的基线。实测未复现时记录尝试与结果，无法执行时记录阻塞和待补测项。
3. **记录文档。** 按项目约定在现有 Bug 列表、问题追踪系统或缺陷文档中新增或更新条目。已有条目沿用原编号。记录问题、分析结论、复现步骤、证据及验证范围。项目没有既定入口时，在现有任务文档中记录。
4. **提出修复方案。** 写明修复依据、拟修改的范围、相关行为及数据影响，以及如何用修复前的场景验证。把方案或其链接补到对应 Bug 条目，注明待确认的问题。
5. **核对修复授权。** 已获修复授权且方案明确时，按目标项目的代码变更流程直接修复。项目要求审批时按项目流程确认。关键行为、修复范围或方案仍有实质未决项时，带上实测结果和拟议方案，集中确认未决项后再修复。方案的关键行为或范围发生变化时，复核现有授权是否覆盖变更。

修复后重跑相关场景，并在原 Bug 条目补记修复结果和验证范围。
